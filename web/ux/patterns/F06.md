# F06 Pembayaran

Status: draf   |   Tanggal riset: 2026-10-01   |   Keyakinan: **sedang**

Keyakinan sedang karena: kriteria aksesibilitas **N/V di seluruh kandidat** (15% bobot hilang,
lihat `web/ux/scores/F06.md`), 4 dari 7 kandidat hanya punya 1 penerbit bukti, dan lubang
`invoice_id` belum punya solusi di API yang ada.

## 1. Tujuan pengguna dan metrik sukses

- **Peran:** Pasien (atau wali yang membayar atas anggota keluarganya). Mobile-first 390 px,
  Android menengah-bawah, jaringan tidak stabil, banyak pengguna lansia.
- **Tujuan:** membayar tagihan pesanan obat yang statusnya `menunggu_pembayaran` sampai
  instruksi bayar diterima (VA/QR), lalu melihat status berubah menjadi lunas.
- **Metrik (terukur):**
  - **<= 3 layar** dan **<= 4 ketukan** dari membuka `/pembayaran/{pesananId}` sampai
    instruksi pembayaran tampil (termasuk 1 field id invoice selama gap API masih ada).
  - **0 field wajib** selain id invoice dan pilihan metode; tidak ada input data diri baru.
  - **100% state** (loading/kosong/error/offline/sukses/parsial) punya aksi lanjut yang
    terlihat.
  - Status lunas hanya dibaca dari server; **0 flag "sudah bayar" lokal** di kode.
  - Semua target sentuh **>= 44 px**, kontras teks **>= 4,5:1** (syarat `web/AGENTS.md`).

## 3. Yang sengaja TIDAK ditiru

- **Grid logo merek 16 metode (Shopee) / daftar 14 metode berlabel brand (Tokopedia)** —
  `web/AGENTS.md` melarang menyalin aset & nama merek; cukup nama teks + tipe + penyedia.
- **Harga bisa berubah di halaman bayar (Traveloka, T&C §1.5)** — terflag sebagai risiko
  kejutan; Traveloka tidak dipakai sebagai sumber pola tampilan harga apa pun.
- **CTA ambigu ala Halodoc** (temuan **KUT6**: *"button ... creates a misperception"*,
  JSI 2021) — tombol ditulis `Bayar sekarang` dan hanya aktif bila semua syarat terpenuhi,
  tanpa tombol kedua yang bersaing.
- **Redirect ke aplikasi dompet pihak ketiga (Gojek/GoPay, Midtrans)** — tidak bisa dibangun
  (tak ada field deep-link di `MulaiPembayaranData`) dan membuat pengguna kehilangan konteks
  di jaringan lambat.
- **Hitung mundur animatif / tekanan waktu** (QRIS Tokopedia 75 detik; ShopeePay 1 jam) —
  TIDAK ditiru; cukup tanggal/jam kedaluwarsa apa adanya + label zona waktu.
- **Biaya tersembunyi / biaya muncul setelah komitmen** — dihindari dengan estimasi biaya di
  picker (label "perkiraan") dan tagihan persis di layar instruksi.
- **Consent terselip, pre-checked asuransi/proteksi, upsell menutupi aksi utama** — tidak
  ada bukti di kandidat mana pun dan dilarang rubrik.
- **Teks/angka Baymard tidak disalin harfiah** — hanya pola yang diparafrasekan; angka
  benchmark (70,19% abandonment dsb.) tidak dipakai sebagai klaim produk Sehatly.
- **QR sebagai gambar** — tidak ditiru sekarang: butuh pustaka baru (dilarang tanpa izin);
  `qr_string` tampil sebagai teks yang bisa disalin.

- **Data dari API (endpoint + field yang dibutuhkan):**
  - `GET /pesanan-obat/{id}` → `pesanan: {id, nomor_pesanan, status, subtotal,
    biaya_kirim, total}` — **satu-satunya sumber status lunas**; polling `refetchInterval`
    15.000 ms, berhenti saat `status` ∈ `STATUS_PESANAN_TERMINAL`.
  - `GET /referensi/metode-pembayaran` (publik) → `metode_pembayaran[]: {id, nama,
    penyedia, tipe, biaya_admin_flat, biaya_admin_persen}` — dikelompokkan per `tipe`
    memakai `TIPE_METODE_URUT`/`TIPE_METODE_LABEL` (9 grup, 14 metode terseed).
  - `POST /invoice/{id}/bayar` body `{metode_id}` → **201** `MulaiPembayaranData`:
    `invoice: {id, nomor_invoice, total}`, `pembayaran: {status, terminal,
    kadaluwarsa_at}`, `toko: {va_number? , qr_string, nama_bank?, nama_pemilik,
    nama_penyedia}`, `instruksi: string[]`, `gateway: {nama, nomor_referensi}`.
    **422** = sudah ada pembayaran pending (`Pembayaran untuk invoice ini sudah dibuat
    dengan nomor referensi X`) / nominal tidak cocok.
  - `POST /promo/validasi` body `{invoice_id, kode}` → 200 `{valid, nilai_diskon, total,
    alasan: [{kode, pesan, kolom}], rincian: {subtotal, diskon, biaya_admin,
    biaya_pengiriman}}` — penolakan = `valid:false`, **bukan** status error.
  - `POST /webhook/payment/{gateway}` — **server only, HMAC-SHA256, tidak pernah dipanggil
    dari browser**; idempoten, settlement menulis `pesanan_obat.status` sekali.
  - **Realtime: TIDAK ADA.** Kanal Reverb hanya `konsultasi.{id}` (F08) → F06 wajib
    polling REST, jangan menunggu event.
- **Label status** memakai helper yang ada (`labelStatusPesanan`, `labelStatusPembayaran`,
  `labelStatusOpsi`), **bukan string manual** (aturan enum di `web/AGENTS.md`).

## 6. State lengkap

| State | Yang dilihat pengguna | Tindakan lanjut |
|---|---|---|
| **Loading** | `SkeletonRows` (6 baris) untuk pesanan; 3 baris untuk daftar metode — **bukan** spinner layar penuh | tidak ada (konten menggantikan sendiri) |
| **Kosong** | Pesanan sudah tidak `menunggu_pembayaran` → Alert `--success` "Pesanan ini sudah lunas" + rincian status | `Lihat lacak pesanan` |
| **Error jaringan** | `ErrorState` + pesan `Pembayaran gagal dimulai. Periksa koneksi lalu coba lagi.` | tombol `Coba lagi` → refetch |
| **Error validasi (klien)** | `FormErrorSummary` di atas form; hint berubah merah `Id invoice harus berupa angka lebih dari 0.` | fokus pindah ke field pertama yang gagal |
| **Error server 422** | Pesan server apa adanya + `data-slot="payment-server-refused"` (bayar ganda / nominal tidak cocok); **form & input TIDAK dikosongkan** | ubah id invoice / metode, ulangi |
| **Error 404/403** | `NotFoundState` "Pesanan tidak ditemukan" / `ForbiddenState` | tautan kembali ke daftar pesanan |
| **Offline** | `navigator.onLine === false` → `Alert` `--warning`: `Tidak ada koneksi. Perubahan belum dikirim.`; tombol `Bayar sekarang` nonaktif; polling dijeda | `Coba lagi` saat online kembali (event `online`) |
| **Sesi habis** | perilaku global single-flight refresh → redirect login (yang sudah ada); form tidak dikirim saat sesi mati | login → kembali ke `/pembayaran/{pesananId}` (input id invoice hilang → isi ulang) |
| **Sukses (settlement)** | Status pesanan berubah → Alert `--success` `Pembayaran tercatat. Pesanan sedang diproses.`; polling berhenti | `Lihat lacak pesanan` |
| **Parsial** | Instruksi tampil tetapi status masih `menunggu` → tetap tampilkan `kadaluwarsa_at` + tombol `Salin`; promo `valid:false` muncul tanpa menghapus instruksi | salin VA, refresh manual |

## 7. Edge case medis dan bisnis

1. **Pembayaran gagal / settlement tertunda** — webhook belum tiba; layar tetap `Menunggu`
   dan polling berjalan. Jangan pernah menampilkan "Berhasil" berdasarkan keberadaan nomor VA
   (fakta: VA ada sebelum uang masuk).
2. **Invoice kadaluwarsa** — `pembayaran.kadaluwarsa_at` lewat → instruksi tetap tampil
   dengan label `Kedaluwarsa` + `text-warning`; aksi `Bayar sekarang` untuk invoice baru
   akan ditolak server 422. Pesan: `Batas waktu pembayaran lewat. Hubungi dukungan untuk
   tagihan baru.` **Tanpa hitung mundur animatif.**
3. **Pembayaran ganda (dua perangkat)** — percobaan kedua kena **422** "sudah dibuat dengan
   nomor referensi X"; webhook ulang dibalas `duplicate: true` tanpa menulis. Layar menampilkan
   pesan 422, lalu mengandalkan polling status pesanan — **tanpa** flag lunas lokal.
4. **Promo ditolak** — `valid:false` dengan `alasan[]` per `kolom` (aktif, jendela WIB,
   min_transaksi, kuota_total, kuota_per_user). Tampilkan tiap `pesan` sebagai daftar; jangan
   menghitung ulang diskon; `kuota` → `text-warning` + catatan "potongannya tidak otomatis
   penuh".
5. **Refund tidak ada** — F12 tanpa endpoint refund (fakta `web/ux/flows.md`): **jangan
   menampilkan** tombol/label refund apa pun di F06. Jika pengguna menanyakan refund → saluran
   dukungan, bukan UI.
6. **Biaya salah metode** — `biaya_admin_flat` + `biaya_admin_persen` berbeda per metode dan
   dihitung atas **subtotal − diskon**; ganti metode setelah inisiasi = pembayaran pending
   lama tetap berlaku → 422. Picker hanya menampilkan **perkiraan**; angka final =
   `invoice.total` dari respons `POST /invoice/{id}/bayar`.
7. **QR tidak persisten server-side** — `qr_string` hanya hidup di respons 201; **reload
   menghapus QR** (kolomnya tidak ada di tabel `pembayaran`, hanya `va_number`). Mitigasi:
   pertahankan data respons di memori selama satu sesi; jika hilang → ulangi inisiasi dan
   siapkan pesan 422 yang bisa ditindaklanjuti. (Pertanyaan terbuka #3.)
8. **Zona waktu** — `kadaluwarsa_at` selalu diformat `formatWaktu` dengan **label zona waktu
   (WIB/WITA/WIT)** sesuai zona pengguna (aturan `web/AGENTS.md`).
9. **Dua perangkat / tab** — tidak ada state server-sent; kedua tab mem-poll sumber yang sama
   dan keduanya berhenti saat status terminal (tidak ada konflik tulis di sisi klien).
10. **Data medis** — layar F06 hanya memuat nomor pesanan/invoice & uang; **tidak ada** nama
    obat, dosis, diagnosa, atau jadwal konsultasi (lihat §9).

## 8. Aksesibilitas

- **Urutan fokus:** status pesanan → id invoice → metode → `Bayar sekarang` → `Salin` (bila
  instruksi tampil) → promo → tautan lacak. Fokus tidak pernah terjebak; `FormErrorSummary`
  menerima fokus saat submit gagal.
- **Label:** semua input lewat komponen `Field` (label terhubung + `required` + hint);
  tidak ada placeholder sebagai label.
- **Target sentuh:** tombol utama & `Select` memakai `min-h-11` (44 px) di 390 px; baris
  ringkasan tidak menjadi target tersembunyi < 44 px.
- **Kontras:** teks utama `--foreground`/`--card-foreground` >= 4,5:1; teks status
  `text-warning` hanya dipakai **bersama ikon + teks** (bukan warna saja), sesuai
  `web/AGENTS.md`.
- **Fokus terlihat:** memakai `--ring` bawaan komponen shadcn (`focus-visible:ring`);
  jangan menghapus ring.
- **Pengumuman pembaca layar:** blok status memakai `aria-live="polite"`; ikon `aria-hidden`;
  perubahan `Menunggu → Lunas` diumumkan lewat region live, bukan hanya warna.
- **Teks besar:** layout memakai flex + wrap; uang `tabular-nums` tidak terpotong; tidak ada
  ellipsis pada data tagihan.
- **Catatan bukti:** kriteria 4 rubrik N/V untuk semua kandidat → syarat di atas berasal dari
  `web/AGENTS.md` (bukan dari aplikasi acuan).

## 9. Privasi

- **Tampil:** nomor pesanan, nomor invoice, status pembayaran, nominal uang, nomor VA/QRIS,
  nama bank/penyedia, nama pemilik rekening sesuai tagihan.
- **Disamarkan:** tidak perlu menampilkan data kartu/kredensial apa pun (F06 tidak mengambil
  kartu); nomor VA tidak perlu disembunyikan (bukan data pribadi sensitif) tetapi **tidak**
  dipotong agar bisa disalin utuh.
- **TIDAK BOLEH muncul di toast / judul tab / URL / notifikasi:**
  - nama obat, dosis, aturan pakai, diagnosa, keluhan, jadwal konsultasi, nama dokter,
    anggota keluarga yang sakit;
  - NIK, alamat, nomor telepon;
  - judul dokumen tetap `Pembayaran`; URL hanya `/pembayaran/{pesananId}` (angka) —
    **tanpa** `invoice_id`, `nomor_resep`, atau parameter uang.
  - Toast hanya memuat pesan server generik (`Pembayaran berhasil dimulai.`), bukan detail
    tagihan + identitas pasien sekaligus.
- **Sesi:** mengikuti refresh single-flight global; layar tidak menampilkan data orang lain —
  404 dipakai untuk menutup keberadaan baris milik akun lain (sudah menjadi perilaku
  `GET /pesanan-obat/{id}`).
- **UU PDP:** karena F06 hanya memproses data tagihan, tidak ada consent baru yang
  ditampilkan; consent medis ada di F02 (belum ada UI — jangan diselipkan diam-diam di F06).

## 12. Pertanyaan terbuka

Keputusan yang butuh persetujuan pemilik produk / backend:1. **`invoice_id` tidak dipublikasikan (P0).** Tidak ada `GET /invoice/{id}` dan checkout
   tidak mengembalikannya → input manual tetap ada. Opsi: (a) checkout 201 menyertakan
   `invoice_id`, (b) `GET /invoice?pesanan_id=`, (c) biarkan manual. Desain §5 mengasumsikan
   (c); begitu (a)/(b) ada, field id invoice dihapus dan metrik turun ke <= 2 layar.
2. **Endpoint status pembayaran.** Satu-satunya tanda lunas = `pesanan_obat.status`. Perlu
   `GET /invoice/{id}` agar layar bisa menampilkan `pembayaran.status` & `kadaluwarsa_at`
   tanpa inisiasi ulang?
3. **QR tidak disimpan server.** Simpan `qr_string` (tambah kolom + endpoint) atau terima QR
   hilang saat reload? (Menampilkan QR sebagai gambar juga butuh pustaka baru → izin stack.)
4. **Preselect metode.** Baymard menyarankan metode paling umum dipilih otomatis; apakah ada
   data metode terpopuler, atau semua default `Pilih metode` (pilihan aman)?
5. **Promo di step pembayaran.** Baymard menyarankan promo di halaman sebelum pembayaran;
   API Sehatly mewajibkan `invoice_id` yang baru ada setelah inisiasi. Pindahkan ke checkout
   (`POST /resep/{id}/checkout` menerima `kode_promo`) atau tetap di sini?
6. **Gateway masih mock.** Konfigurasi mendukung midtrans/xendit/doku/flip tetapi
   implementasinya mock → AC-4/6/7 diuji dengan mock. Kapan uji ke gateway sungguhan
   (sandbox) dijadwalkan?
7. **Offline lintas-flow.** F15 mencatat offline belum ditangani sama sekali. Apakah F06 yang
   memulai pola banner offline global (rekomendasi: ya, agar F05/F08/F09 memakai hal yang
   sama)?
8. **Refund absen (F12).** Tidak ada endpoint refund; dipastikan F06 tidak menampilkan opsi
   refund, atau ada rencana backend tersembunyi?
9. **`web/ux/patterns/_global.md` belum ada** (dirujuk `web/AGENTS.md`) — siapa yang membuat
   pola lintas flow (status, tombol, offline, toast) sebelum implementasi F06?

### Koreksi implementasi (2026-10-01, sesi F06)

Pattern di atas ditulis saat `GET /invoice/{id}` belum ada. Backend sekarang menyediakannya
(`auth:sanctum` + `permission:pembayaran.bayar`, owner-only, invoice milik pasien lain =
404) dan resource-nya memublikasikan `invoice.pembayaran` (terbaru dulu). Yang berubah dan
yang tidak:

1. **Q1/Q2 terjawab sebagian.** `GET /invoice/{id}` ADA dan dipakai layar untuk memvalidasi
   id yang diketik serta menampilkan status tagihan, total, jatuh tempo, dan riwayat
   pembayaran. Input manual **tetap ada**: checkout tetap tidak mengembalikan `invoice_id`
   dan tetap tidak ada daftar invoice, jadi id tidak bisa ditemukan otomatis. Bila suatu saat
   checkout memublikasikan `invoice_id`, field manual dihapus sesuai Q1.
2. **Sinyal settlement tidak berubah.** Yang menandai pesanan diproses tetap
   `pesanan_obat.status` (bukan `invoice.status`, bukan keberadaan VA). §4 tetap berlaku;
   §5 baris peringatan "tidak ada endpoint status pembayaran" sudah tidak relevan dan
   digantikan copy yang menyebut status tagihan dibaca dari server.
3. **Koreksi AC-6 vs §4.** §4 langkah 7 menulis polling "berhenti di status terminal",
   padahal `STATUS_PESANAN_TERMINAL` hanya `['selesai','dibatalkan']` — dengan definisi itu
   polling terus berjalan sia-sia setelah `diproses`. AC-6 dan tabel §11 (call-2 = `diproses`,
   tidak ada panggilan ke-4 dalam 45 detik) menang: **polling berhenti begitu status
   meninggalkan `menunggu_pembayaran`**. Implementasi memakai syarat itu.
4. **Q3 masih terbuka.** `qr_string` tetap tidak disimpan server; hanya `va_number` yang
   persisten, sehingga muat ulang tetap menghapus QR. Riwayat dari `GET /invoice/{id}`
   menampilkan VA + status + referensi untuk pembayaran berjalan, tetapi tidak QR-nya.
5. **AC-8 offline** memakai primitif F15 (`OfflineBanner`, `useOnlineStatus`) tanpa antrean
   mutasi; polling dijeda dan tombol `Coba lagi` milik layar yang memulai ulang, sehingga
   `refetchOnReconnect` dimatikan khusus di query pesanan layar ini.
6. **Promo lebih awal (§2 langkah 8 dikoreksi).** Karena `GET /invoice/{id}` sudah memverifikasi
   id yang diketik, form promo kini aktif begitu id invoice valid — tidak lagi menunggu
   `POST /invoice/{id}/bayar`. Server tetap satu-satunya yang menghitung diskon (`valid:false`
   = 200), dan alasan penolakan tetap ditampilkan apa adanya. Ini juga menghapus satu-satunya
   alasan urutan "promo di bawah instruksi" (invoice_id yang belum ada).
7. **Jalur keluar 404/403.** `NotFoundState`/`ForbiddenState` di layar ini kini membawa tombol
   `Lihat lacak pesanan` sesuai `_global.md` §1.2.3; sebelumnya kartu 404 tidak punya tindakan
   lanjut.
8. **Layout desktop §5 masih satu kolom**, bukan dua kolom seperti sketsa. AC-9 hanya mengukur
   390 & 1280; grid dua kolom dicatat sebagai usulan, belum diimplementasikan agar tak
   membangun ulang layar yang sudah bekerja.
