# F14 Admin klinik (dokter, jadwal, laporan)

Status: draf   |   Tanggal riset: 2026-10-02   |   Keyakinan: **sedang** (dokumen help/vendor publik + regulator; **tidak ada UI admin Sehatly dan tidak ada backend admin** — semua kontrak API di §4 adalah USULAN, bukan yang ada. Lihat `web/ux/scores/F14.md`.)

> **Peringatan blokir backend.** F14 adalah flow **greenfield**. `docs/openapi.yaml` memuat **41 path** dan **nol** path admin; `routes/api.php` tidak memiliki satu route admin pun; `dokter_jadwal`/`dokter_libur` hanya bisa dibaca lewat `GET /dokter/{id}/jadwal` publik; `audit_log` tidak punya endpoint baca; tidak ada endpoint agregasi laporan. **Implementasi UI F14 tidak boleh dimulai sebelum kontrak §4 disetujui dan endpoint-nya ada.** Rincian: `web/ux/evidence/F14/sehatly-fase0.md`.

## 1. Tujuan pengguna dan metrik sukses

- Peran: **admin klinik** (operasional, tidak selalu teknis, sering berbagi satu komputer depan; dominan desktop 1280 px, sesekali 390 px saat keliling).
- Tujuan: (a) memastikan **dokter yang tampil ke pasien benar-benar layak** (verifikasi kredensial, STR/SIP belum kedaluwarsa, aktif); (b) menjaga **jadwal praktik mingguan akurat** tanpa bentrok; (c) membaca **laporan booking/pendapatan/kehadiran** periode tertentu; (d) mengetahui **siapa mengubah apa** (audit) dan batas izin tiap peran.
- Metrik terukur:
  - **≤ 3 layar & ≤ 5 ketukan** dari daftar dokter sampai status dokter berubah (verifikasi/nonaktif), termasuk dialog konfirmasi (AC-2, AC-3).
  - **1 form multi-hari** untuk membuat jadwal rutin 3 hari + **1 pratinjau slot**; **≤ 8 field** per pengiriman (AC-4).
  - Laporan 30 hari tampil dari **≤ 3 request paralel** dan rentang berubah dengan **1 ketukan chip** (AC-8).
  - Aksi massal 10 dokter: **1 dialog blast-radius** (jumlah + nama + booking terdampak) dan **hasil per-dokter** tanpa kegagalan senyap (AC-7).
  - Audit: **0 tombol** ubah/hapus/export di layar; nilai sensitif termasking (AC-10, AC-14).
  - Semua kontrol ≥ 44 px; kontras ≥ 4,5:1; axe 0 pelanggaran (AC-13).
  - **0 data kredensial** (nomor STR/SIP penuh) di URL, judul tab, atau toast (AC-14).

## 3. Yang sengaja TIDAK ditiru

- **Trustmedis: hapus jadwal tanpa dialog konfirmasi** (hanya notifikasi bila gagal). Sehatly memakai dialog konfirmasi + jalur "Nonaktifkan" (pola §4 `_global.md`); aksi destruktif tidak boleh satu klik.
- **Trustmedis: hirarki menu dalam** (Admisi → Back Office → Jadwal Dokter) dan **form akun 20+ field dengan 9 toggle autorisasi**. Sehatly memakai sidebar admin datar (`Dokter`, `Jadwal`, `Laporan`, `Audit`) dan izin hanya dari `RbacCatalog` — bukan toggle per pengguna yang diciptakan ulang.
- **Trustmedis: persetujuan atasan via ketik ulang username+password** (approval-by-impersonation). Sehatly tidak meniru; aksi sensitif = izin peran + audit, bukan kata sandi kedua.
- **Practo Ray: aksesibilitas rusak-terdokumentasi** (audit 2025 isu kritis 7/9 layar iOS + perintah pengadilan 2022) → **dilarang** jadi acuan aksesibilitas; Sehatly memakai WCAG + kebijakan 44 px.
- **Practo Ray: cross-sell produk di navigasi** dan **fitur khusus negara** (Singapore/Philippines) → nav admin Sehatly bersih dan fitur tidak digembar-gemborkan berbeda per wilayah.
- **Jane: override jadwal hanya dengan peringatan** dan **tidak bisa pilih multi-staf untuk export** → Sehatly memakai **dialog konfirmasi perubahan jadwal** yang menyebut rentang + jumlah shift terdampak, dan tidak menjanjikan export multi-dokter.
- **Klinik Pintar: tambah jadwal per hari secara berulang** (satu form per hari, tanpa salin) → Sehatly memakai form multi-hari + salin jam (Jane).
- **Shopify: activity log tanpa ekspor dan batas 250 baris** sebagai satu-satunya jejak → Sehatly memakai `audit_log` yang memang bisa difilter & dipaginasi (bukan daftar terpotong 250 tanpa penjelasan); **tetap tanpa export** karena tidak ada endpoint, dan catatan itu ditulis di layar.
- **GitHub: pencarian audit tanpa teks bebas** (hanya sintaks query) → Sehatly memakai filter dropdown terstruktur + pencarian nama aktor, bukan bahasa query.
- **Semua merek, ikon khas, ilustrasi, teks asli, nama menu asli** tidak disalin; hanya pola interaksi. Tidak ada dialog "Anda yakin?", tidak ada hitung mundur, tidak ada upsell.

### 4.6 Data/API per langkah (semuanya USULAN kecuali yang disebut)

1. **Muat daftar dokter**: `GET /admin/dokter?...` (usulan #1). 3 request paralel maksimum: daftar, `GET /referensi/spesialisasi` (sudah ada, publik), `GET /me` (shell, tidak dihitung).
2. **Detail & dampak**: `GET /admin/dokter/{id}?include=dampak` (usulan #2) + `GET /admin/dokter/{id}/jadwal` (usulan #5) saat tab jadwal dibuka.
3. **Verifikasi**: `PUT /admin/dokter/{id}/verifikasi` (usulan #3) → 200; 422 bila status bukan `pending` (race dua admin) → alert inline + refetch.
4. **Aktivasi/nonaktif**: `PUT /admin/dokter/{id}/status` (usulan #4); dampak diambil **sebelum** dialog.
5. **Jadwal CRUD**: usulan #5–#8; libur #9; publish = `PUT /admin/jadwal/{id}` `status_aktif=true` (atau dibuat `status_aktif=false` lalu diterbitkan sekaligus) — keputusan kontrak §12. **Rutin vs satu kali:** `dokter_jadwal` adalah pola **mingguan berulang** (`hari` 0–6); sesi satu kali hanya bisa direpresentasikan sebagai baris dengan `berlaku_mulai = berlaku_sampai` pada `hari` yang cocok. Bila tanggal itu sudah terisi jadwal rutin, sistem **menolak karena overlap** — jadi "tambahan satu kali di atas jadwal rutin" belum didukung dan tidak boleh ditawarkan UI (edge #19).
6. **Laporan**: usulan #12–#13; dua request paralel (booking & pendapatan), panel independen.
7. **Audit**: usulan #14; data sudah diredaksi saat **tulis** (`AuditColumnPolicy`), UI hanya membaca.
8. **Realtime**: **tidak ada** kanal Reverb baru. Gunakan refetch saat window focus + tombol "Muat ulang"; jangan menjanjikan live. (Satu-satunya kanal Reverb produk = `konsultasi.{id}`; `routes/channels.php`.)

## 7. Edge case medis dan bisnis

1. **STR kedaluwarsa / mendekati**: `str_berlaku_sampai` NOT NULL (`sehatly-fase0.md` S6). Badge `--warning` bila ≤60 hari, `--destructive` bila lewat. **STR seumur hidup tidak representable** — jangan tampilkan "berlaku selamanya"; §12 #4.
2. **SIP kosong vs SIP tidak wajib**: `sip_berlaku_sampai` nullable; tampilkan "Belum diisi" (netral) — jangan menyimpulkan ilegal.
3. **Nonaktifkan dokter yang punya booking aktif**: dialog menampilkan jumlah; **tidak ada pembatalan otomatis**; booking tetap berjalan dan muncul di laporan. Jalur ini sengaja tidak diblokir agar kredensial bermasalah bisa segera dihentikan (alasan keselamatan pasien).
4. **STR/SIP dinonaktifkan regulator di luar aplikasi** (`regulasi S4`): admin memutuskan manual; tidak ada integrasi Kemenkes → jangan menjanjikan validasi otomatis.
5. **Overlap jadwal**: dua baris `(dokter, hari)` dengan jam beririsan dilarang **oleh validasi aplikasi** (skema tidak mencegah, `fase0 S4,S7`). Form memvalidasi di klien untuk UX dan server menolak dengan 422 (server tetap otoritas).
6. **`hari=7`/`berlaku_sampai < berlaku_mulai`/`jam_selesai <= jam_mulai`**: skema mengizinkan (`fase0 S7`) → validasi server + klien wajib; pesan spesifik.
7. **`kuota_per_sesi = NULL` vs `0`**: NULL = tanpa kuota, 0 = tidak ada slot. UI memakai checkbox "Batasi kuota" + field angka; jangan pernah mengirim 0 dari field kosong.
8. **Libur setengah hari**: tidak bisa disimpan (`fase0 S5`); UI menuliskan keterbatasan; alternatif = nonaktifkan jadwal hari itu (mingguan) — dengan konsekuensi minggu berikutnya ikut nonaktif, dinyatakan di dialog.
9. **Hapus jadwal yang punya booking**: 422 + tombol "Nonaktifkan saja" (pola Trustmedis).
10. **Dua admin menyunting jadwal bersamaan**: server menolak dengan 409/422 + baris terbaru; UI menampilkan alert + refetch, isi form tidak dihapus (pengguna bisa bandingkan dulu).
11. **Bulk partial failure**: 3 dari 10 gagal (mis. booking aktif) → daftar hasil per-dokter dengan alasan; jangan toast "berhasil" global.
12. **Laporan kehadiran & `no_show`**: status `no_show` ada di enum tetapi **tidak punya penulis** (`fase0 S12`) → laporan menampilkan selesai/dibatalkan/kadaluarsa; baris "tidak hadir" **tidak** ditampilkan sampai endpoint penulis ada. Jangan menampilkan 0 yang menyesatkan.
13. **Pendapatan vs cacat ledger F12**: `BookingService::batalkan()` mengubah invoice → `dibatalkan` tanpa cek pembayaran & tanpa baris refund (cacat P0 F12). Laporan pendapatan **wajib** membawa `meta.peringatan_ledger` dan UI menampilkan alert; angka berbasis `invoice.lunas_at`/`pembayaran.dibayar_at` dinyatakan sebagai dasar.
14. **Admin tidak boleh membaca klinis**: role admin tidak memegang `rekam_medis.lihat`/`resep.lihat` (`fase0 S2`); laporan agregat, tanpa diagnosis/obat. Request 403 → `ForbiddenState`.
15. **`pdp.kelola` baca-saja**: admin tidak boleh mencatat/menarik consent atas nama pengguna (komentar `routes/api.php` ~1393-1399); halaman consent hanya ledger read-only.
16. **Audit `record_id` VARCHAR**: `dokter_faskes` dsb. memakai PK komposit `"12|34"` (`fase0 S8`); UI menampilkan apa adanya, tidak mengurai angka.
17. **Zona waktu**: jadwal = jam dinding Indonesia; label "WIB" default. Klinik WITA/WIT belum didukung stack → §12 #9; laporan memakai rentang tanggal zona pengguna (label di header).
18. **Sesi dokter yang dinonaktifkan**: token dokter yang sudah login tidak otomatis mati (tidak ada backend); catat sebagai kebutuhan backend (cek `status_aktif` saat refresh/token berikutnya) — §12 #8.
19. **Jadwal satu kali (one-off)**: skema hanya mengenal `hari` mingguan + rentang `berlaku_mulai`/`berlaku_sampai`; sesi tambahan satu kali di atas jadwal rutin **tidak representable tanpa aturan override** (akan bertabrakan). UI tidak menampilkan tombol "Tambah sesi satu kali"; yang tersedia hanya "Jadwal rutin" dan "Libur seharian". Bila nanti dibutuhkan, itu keputusan kontrak baru (mis. tabel override/pengecualian) — §12 #12.

## 8. Aksesibilitas

- **Urutan fokus daftar**: header (judul → Muat ulang) → pencarian → chip filter → checkbox Select All → action bar → checkbox baris + "Buka" per baris → pagination. Aksi massal diekspos setelah seleksi, dan pengumuman `aria-live="polite"` membaca "3 dokter dipilih".
- **Dialog**: Radix focus-trap; fokus awal ke tombol non-destruktif; `Esc` menutup; fokus kembali ke pemicu; konfirmasi type-to-confirm mengumumkan sisa yang harus diketik; tombol destruktif `variant="destructive"` **tidak** bersebelahan langsung dengan tombol utama tanpa `separator`.
- **Target ≥ 44 px** untuk checkbox, chip, tombol baris, aksi massal (`h-11`). Checkbox baris memiliki `aria-label` nama dokter ("Pilih Dr. Budi Santoso").
- **Tidak warna saja**: status = teks + ikon (`CircleCheck`, `Clock`, `TriangleAlert`, `CircleX`) + warna; STR warning memuat teks "58 hari lagi".
- **Kontras ≥ 4,5:1**; `--success`/`--warning` hanya untuk ikon/latar lembut, teks status memakai `--foreground` (pelajaran F13 #15).
- **Tabel = grid baris** dengan `role="list"`/`listitem` atau `<table>` semantik sederhana; header desktop `sticky`; tidak ada `truncate`/`line-clamp` pada nomor STR/SIP termasking, tanggal, atau angka uang (wrap/kolom melebar).
- **Teks besar/zoom 200%**: tanpa tinggi tetap; form Sheet bisa di-scroll; tombol tidak mengecil.
- **Form jadwal**: field berlabel eksplisit (`Field`), pesan error `aria-describedby`, ringkasan error di atas form `role="alert"`, hari sebagai checkbox group dengan `<fieldset><legend>Hari</legend>`.
- `expectNoA11yViolations` (`web/tests/e2e/a11y.ts`, `@axe-core/playwright`) di setiap AC layar; axe = subset WCAG → uji keyboard/SR manual.

## 9. Privasi

- **Tidak boleh muncul di** toast, `document.title`, URL, atau notifikasi push: nomor STR/SIP penuh, nama pasien, diagnosis, nominal spesifik per pasien. Judul tab: "Dokter" / "Jadwal dokter" / "Laporan" / "Jejak audit" (atau nama dokter pada halaman detail — nama dokter bukan data pasien; tetap hindari nomor kredensial).
- **Nomor STR/SIP dimasking** di list & detail (`33••••••••••12`); angka penuh hanya dalam berkas yang dibuka dengan `dokter.kelola` + signed URL, tidak pernah dirender sebagai teks halaman. Selaras `AuditColumnPolicy` (yang sudah memasking `nomor_str` dan menolak `file_str_url`/`file_sip_url` masuk audit).
- **URL filter hanya non-sensitif**: `?status_verifikasi=pending&page=2` / `?dari=2026-09-01&sampai=2026-09-30`; jangan menaruh nama dokter di query.
- **Laporan = agregat**: tanpa nama pasien, keluhan, diagnosis, obat. Kartu "kehadiran" hanya persentase; rincian harian = tanggal + jumlah + nominal total.
- **Audit**: `data_lama`/`data_baru` sudah diredaksi saat tulis (`AuditColumnPolicy`: teks naratif ditolak, NIK/STR/telepon/email dimasking); UI tidak menambah kolom mentah; tanpa export (tidak ada endpoint; egress massal harus lewat `audit_log.aksi='export'` di masa depan bila diputuskan).
- **PDP read-only**: halaman consent menampilkan status per pengguna; admin tidak mengubah. Jangan tampilkan isi consent di toast.
- **Screen sharing**: toast generik ("Status dokter diperbarui.") aman di layar bersama; dialog verifikasi menampilkan hanya nomor masking.
- Notifikasi server yang sudah ada sudah generik — jangan menambah payload medis untuk kebutuhan admin.

## 12. Pertanyaan terbuka

1. **Kode izin baru wajib** — `dokter.kelola`, `jadwal.kelola`, `laporan.lihat` **tidak ada** di `RbacCatalog::PERMISSIONS` (24 kode). Menambah kode = perubahan data RBAC + re-seed + update tes katalog. Setujui daftar kode & siapa pemegangnya (admin + superadmin? apoteker/kurir tetap nol)? Tanpa ini, endpoint admin tidak bisa ditulis.
2. **Nonaktifkan dokter yang masih punya booking aktif**: (a) izinkan + tampilkan blast radius (usulan pattern — alasan keselamatan), (b) blokir total, atau (c) izinkan + tawarkan alur jadwal ulang massal (butuh F12 dulu)? Keputusan pemilik.
3. **Alasan penolakan verifikasi**: `dokter.status_verifikasi` hanya 3 nilai tanpa kolom alasan; `AuditColumnPolicy` menolak teks bebas dari `audit_log`. Tambah kolom (migrasi + registry `docs/schema-notes.md` + `verify-schema`) atau penolakan tanpa alasan?
4. **STR seumur hidup (UU 17/2023)**: `str_berlaku_sampai NOT NULL` tidak bisa menyatakan "berlaku seumur hidup" (`regulasi S2,S3`). Tambah kolom flag/semantik NULL (drift, perlu persetujuan) atau tetap tampilkan tanggal dan biarkan admin mengisi tanggal jauh?
5. **Dasar angka pendapatan & dependensi cacat F12**: laporan dihitung dari `invoice.lunas_at` atau `pembayaran.dibayar_at`? Selama `BookingService::batalkan()` menandai invoice batal tanpa refund (P0 F12), laporan harus membawa peringatan. Perbaiki F12 dulu atau rilis dengan `meta.peringatan_ledger`?
6. **Laporan kehadiran & `no_show`**: `no_show` tidak punya penulis. Rilis laporan tanpa "tidak hadir", atau tambah endpoint penulis (F13 §12 #4) lebih dulu?
7. **Publish jadwal**: pola mana yang disetujui — (a) baris dibuat `status_aktif=false` lalu diterbitkan lewat aksi terpisah, atau (b) status aktif per baris langsung saat simpan + tombol "Terbitkan semua draf"? Keduanya mengubah kontrak `POST /admin/dokter/{id}/jadwal`.
8. **Retensi & pembaca audit log**: berapa lama `audit_log` disimpan (NIST menyarankan retensi terencana; UU PDP tidak memberi angka di sumber yang dibaca), dan apakah admin boleh membaca semua tabel atau dibatasi (mis. tanpa `pembayaran`)? `audit.lihat` sudah ada di role admin — konfirmasi cakupannya.
9. **Zona waktu klinik WITA/WIT**: stack saat ini mengasumsikan Asia/Jakarta. Dukungan zona per faskes (butuh kolom/konfigurasi baru + perubahan `SlotAvailabilityService`) atau deklarasikan produk = WIB dulu dengan label jujur?
10. **Aksi massal maksimum**: batas 50 id per request dan hanya dua aksi (`aktifkan`/`nonaktifkan`) — cukup? Verifikasi massal tidak diusulkan (keputusan per dokter).
11. **Halaman PDP read-only** (`pdp.kelola`): apa pertanyaan operasional yang harus dijawab halaman ini (mis. "permintaan akses subjek data"), karena route consent pemilik data tidak boleh diubah admin?
12. **Sesi satu kali (one-off) & override jadwal rutin**: butuh tabel pengecualian (mis. `dokter_jadwal_override`) atau cukup libur seharian + edit jadwal rutin untuk v1? Jika tidak, UI tetap tanpa tombol "sesi satu kali" dan keterbatasan dituliskan (edge #19).
