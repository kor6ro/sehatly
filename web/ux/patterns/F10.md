# F10 Riwayat dan rekam medis

Status: draf   |   Tanggal riset: 2026-10-01   |   Keyakinan: **sedang**
(bukti kuat dari dokumen resmi/manual/store listing; skrin aplikasi acuan di balik login tidak terlihat — lihat `web/ux/scores/F10.md` bagian TIDAK TERVERIFIKASI. **Pemenang aturan rubrik: Mobile JKN (3,50; 70% bobot; ≥3 penerbit)**, tetapi disintesis sebagai **best-of per langkah** karena hitungan end-to-end tak ada di kandidat mana pun.)

## 1. Tujuan pengguna dan metrik sukses

- Peran utama: **pasien** (Android menengah-bawah, lansia termasuk). Turunan: dokter/apoteker tidak diubah di sini (dokter sudah punya editor rekam medis).
- Tujuan pasien: dari satu halaman riwayat, **menemukan rekam medis/surat/kunjungan lama → membacanya utuh → (bila perlu) menyimpannya**, tanpa mengetik id dan tanpa bertanya ke siapa pun.
- Metrik terukur:
  - **≤ 2 ketukan** dari `/rekam-medis` sampai isi rekam medis terbaca (AC-1).
  - **0 panggilan `GET /rekam-medis/{id}`** saat memuat daftar — daftar tidak boleh membakar baris `akses_rekam_medis_log` (AC-2).
  - **0 elemen** teks medis terpotong ellipsis di 390 px (AC-3).
  - **100%** target sentuh utama ≥ 44 px; kontras teks utama ≥ 4,5:1 (AC-4, AC-5).
  - Semua state (loading/kosong/error/offline/404) terpicu dan punya jalan keluar (AC-6, AC-7).
  - **0 data medis** di judul tab, URL, dan toast (AC-10).

## 3. Yang sengaja TIDAK ditiru

- **NHS App: "tidak bisa unduh hasil tes" + pemotongan riwayat "sebelum Oktober 2023"** (dokumen resmi, 2026-10-01): dead-end dan cutoff buatan. Sehatly menawarkan print (interim) dan hanya menampilkan apa yang benar-benar ada — tanpa janji retro-data.
- **MyChart: password PDF yang dapat diprediksi** (`[MMDDYYYY]*JHHS#6!`, tip sheet faskes 2022 via indeks 2026-10-01) dan **biaya salinan formal**; nama menu bervariasi per faskes. Tidak disalin; tidak ada lapisan password karangan di Sehatly.
- **Apple Health: ekspor hanya XML menyeluruh** (bukan per rekaman) dan **notifikasi berisi data medis** (detak jantung tinggi ikut terlihat saat berbagi, `support.apple.com/en-us/guide/iphone/iph5ede58c3d/ios`, 2026-10-01). Jangan taruh data medis di notifikasi/toast (rubrik red flag).
- **Halodoc: riwayat kesehatan dipajang di bawah "Riwayat Transaksi"** (kerangka transaksi menyesatkan) + **klausul pelepasan tuntutan** S&K 6.1.13–6.1.14 (beban risiko dipindah ke pengguna). Sehatly memakai label klinis jujur.
- **SATUSEHAT: pengiriman data kesehatan by default + akses BPJS/Dinas** (`platform/terms-and-privacy`, 2026-10-01) — kebijakan platform, bukan pola UI yang bisa kami tiru; **MySiloam: diagnostics untuk tracking iklan** (App Store App Privacy, 2026-10-01); **Mobile JKN: kebijakan privasi hanya menaut ke homepage** — tidak ditiru; **Alodokter**: tugas inti tak terbukti ada → tidak jadi sumber.
- **Bank: grouping dengan drag kolom & kapasitas 1.000/2.500 baris** (`cpsportal.jackhenry.com`, `merchanthelp.bankofamerica.com`, 2026-10-01) — pola desktop power-user & batas server; Sehatly memakai pagination proyek. **Infinite scroll untuk daftar riwayat tidak dipakai** (Designpixil: paginasi hampir selalu lebih baik untuk tabel data).
- **Tidak ada**: `ui/tabs`, `ui/table`, `ui/accordion`, `ui/popover`, `ui/progress`, `ui/command` (tidak ada di kit); ARIA `role="grid"` untuk daftar statis (APG: pakai `table`/daftar biasa); membaca isi rekam medis untuk fitur pencarian (akan membakar N baris log).
- Semua nama merek, ikon khas, ilustrasi, dan teks asli tidak disalin; hanya pola interaksi. Kandidat domain lain tanpa artikel khusus timeline (NN/g "timeline design" **TIDAK TERVERIFIKASI**, jangan disitasi).

- **Data/API (endpoint yang benar-benar ada; urutan = urutan render)**:
  - `GET /pasien/resep` (`page`, `per_page` maks 100, `status` enum 8 nilai) → **sumber id rekam medis**: `resep[].{id, nomor_resep, tanggal_resep, status, is_kedaluwarsa, berlaku_sampai, konsultasi_id, rekam_medis_id}`; urut server terbaru-dulu; dedupe `rekam_medis_id` via `daftarRekamMedis()` (`tujuan.ts`, `null` di-drop — tidak pernah mengarang id).
  - `GET /pasien/surat-keterangan` (`per_page`, paginasi meta top-level) → `surat_keterangan[].{id, nomor_surat, tipe, tanggal_mulai, tanggal_selesai, jumlah_hari, qr_token, dokter.nama_lengkap}`; relasi sudah di-eager (`pasien.user`, `dokter.user`, `rujukan`).
  - `GET /pasien/booking` (`permission:booking.lihat`) → `booking[].{id, nomor_booking, tanggal_kunjungan, slot_mulai, slot_selesai, tipe_layanan, status, keluhan, dokter_id}` — **resource tidak punya `dokter.nama`** → label `Dokter #{id}` (fallback yang sudah dipakai `booking-list.tsx`); **tidak ada `konsultasi_id`** → baris kunjungan TIDAK bisa dirangkai ke rekam medis (Pertanyaan terbuka #4).
  - `GET /rekam-medis/{id}` → dokumen penuh + 4 anak + `ran[]` (versi naik, tak terpotong) + `adalah_versi_terkini`; **menulis tepat 1 baris `akses_rekam_medis_log`**; non-pihak → **404** (bukan 403); akun tanpa profil → 403. **Aturan keras: 1 baris daftar ≠ prefetch detail.**
  - `GET /surat-keterangan/{nomor_surat}/verify?token=` → publik, selalu 200, hanya `{valid, nomor_surat, tipe, dokter, tanggal, pasien_nama_masked}` (salah token/nomor tak ada = byte sama; token tanpa `?token=` = 422). Token di query hanya untuk verifier publik (aturan `_global.md` §1.2 #4); halaman verifier web = Pertanyaan terbuka #6.
  - **TIDAK ADA (dependensi yang ditandai):** daftar/linimasa rekam medis (`GET /rekam-medis`), pencarian isi rekam medis server-side, endpoint unduh/ekspor (PDF/CSV), pembacaan log akses oleh pasien, PDF surat keterangan (`file_url` selalu `NULL`).
  - Realtime: **tidak ada** (F10 bukan kanal Reverb).

## 6. State lengkap

| State | Yang dilihat | Tindakan lanjut |
|---|---|---|
| Loading | `SkeletonRows` per segmen aktif (bukan spinner layar penuh) | — |
| Kosong (semua sumber) | `EmptyState` + CTA: rekam medis → "Cari dokter"; surat/kunjungan → "Lihat booking saya" | → `/dokter`, `/booking` |
| Kosong (karena filter/pencarian) | Pesan status: "Tidak ada data yang cocok." + tombol "Hapus penyaring" (bedakan dari kosong-sebenarnya, `isEmptyPage`) | hapus filter, 1 ketukan |
| Error jaringan/server | `ErrorState` "Gagal memuat riwayat." + "Coba lagi" (per segmen — segmen lain tetap terpakai) | refetch segmen itu |
| Error hak akses | Dokter/akun tanpa profil → `ForbiddenState` (daftar turunan milik pasien) | kembali |
| 404 detail | `NotFoundState` "Rekam medis tidak ditemukan — tidak ada atau bukan milik akun ini." + "Daftar rekam medis saya" | → `/rekam-medis` |
| Offline | Banner atas "Anda sedang offline. Menampilkan data terakhir yang tersimpan."; data cache `staleTime: 30_000`; tombol filter/pencarian tetap (klien), refetch ditunda | online → banner hilang + refetch |
| Sesi habis | Refresh single-flight → redirect login (perilaku global F15) | login → kembali ke URL semula |
| Sukses | Salin nomor surat → toast sonner **generik** "Nomor surat disalin." (tanpa tipe/diagnosis/isi); print → `window.print()` tanpa toast data medis | lanjut |
| Parsial | Segmen surat gagal sementara rekam medis tampil → hanya segmen itu menampilkan `ErrorState` (bukan seluruh halaman) | retry per segmen |
| Hasil pencarian/filter | `role="status"`: "12 data ditemukan." / "Tidak ada data yang cocok." | — |

## 7. Edge case medis dan bisnis

1. **Belum ada rekam medis sama sekali** (tanpa resep/surat/kunjungan): `EmptyState` per segmen + CTA nyata; jangan menampilkan layar kosong tanpa penjelasan (NN/g 2021).
2. **Resep tanpa rekam medis** (`rekam_medis_id === null` — dokter belum menulis): baris tampil dengan "Belum ada rekam medis untuk resep ini." **non-klik**; jangan mengarahkan ke 404 dan jangan mengarang id (`tujuan.ts` = `null` pertama).
3. **Rekam medis milik pasien lain** (id ketik manual / tautan basi): server menjawab **404** (bukan 403, agar keberadaan baris tidak bocor lintas tenant) → `NotFoundState` + jalan kembali; layar tidak pernah menampilkan cuplikan data medis.
4. **Rantai amandemen**: `ran[]` tampil **penuh, naik, tak terpotong**; entri "terkini" diberi `VersiBadge` + label "terkini"; entri lama = link ke `/rekam-medis/{id}` revisi — **satu ketukan = satu bacaan = satu baris log** (bukan kesalahan, ini akuntansi yang benar). Blok "RIWAYAT VERSI" disembunyikan sama sekali bila `ran.length <= 1`.
5. **Resep kedaluwarsa** (`is_kedaluwarsa=true`): badge `Kedaluwarsa` di baris; **tautan ke rekam medis tetap ada** — kedaluwarsa adalah status resep, rekam medis tetap sah dibaca. Jangan memblokir bacaan dengan status obat.
6. **Transparansi log akses**: notice wajib di detail; **endpoint membaca log belum ada** → pasien belum bisa melihat *siapa* yang membuka (Pertanyaan terbuka #3; jangan mengarang daftar akses).
7. **Offline**: membuka detail dari cache = bacaan TIDAK tercatat (tidak ada jaringan) — terima sebagai batasan `staleTime 30_000` yang sudah disepakati; jangan menambah `staleTime`/`gcTime` infinity (aturan `rekam-medis.ts`).
8. **Teks besar / lansia / zoom 200%**: semua teks medis wrap (`text-base` minimum, diagnosis/keluhan `text-lg` boleh), layout wrap bukan tinggi tetap (WCAG 1.4.4/1.4.10; reflow 320 px tanpa scroll horizontal).
9. **Jam & zona**: `tanggal_periksa` (instan) → `formatWaktu` + label WIB/WITA/WIT; `tanggal_kunjungan`/`jadwal_kontrol` (dinding, `Y-m-d`) → `formatTanggal` **tidak pernah** `formatWaktu` (geser hari).
10. **Dua perangkat/buka ganda**: idempoten — daftar dan detail hanya bacaan; buka ganda = dua baris log (memang benar, lihat logger: dua bacaan dalam 1 detik = dua baris).
11. **Akun dokter membuka `/rekam-medis`**: `ForbiddenState` dengan penjelasan bahwa daftar turunan ini milik pasien (perilaku sekarang dipertahankan sampai endpoint daftar untuk dokter ada).
12. **Anggota keluarga**: baris booking/kunjungan mengikuti cakupan server (`PasienRecordAccess`); jangan menampilkan data anggota keluarga di segmen rekam medis tanpa endpoint yang mendukung.

## 8. Aksesibilitas

- **Urutan fokus**: kembali → pengalih tampilan → pencarian → filter status → baris (per grup waktu) → pagination; di detail: kembali → notice → identitas → SOAP → riwayat versi → aksi cetak.
- **Struktur heading** (H42/SC 2.4.6): `h1` = judul halaman; `h2` = judul segmen ("Rekam medis"); `h3` = grup waktu ("Oktober 2026") dan blok ("Keluhan utama"). Daftar = `<ul>/<li>` (H48); **tanpa** `role="grid"` (APG: daftar statis bukan grid).
- **Target sentuh ≥ 44 px** (aturan Sehatly; WCAG 2.5.8 minimal 24×24 CSS px — angka Sehatly lebih ketat) untuk baris, pengalih, chip filter, CTA, pagination.
- **Kontras ≥ 4,5:1** (SC 1.4.3) teks `--foreground`/`--muted-foreground` di atas `--card`; status selalu **teks + ikon + warna** (jangan warna saja).
- **Pengumuman pembaca layar**: jumlah hasil & pesan kosong/filter = `role="status"` + `aria-live="polite"` (SC 4.1.3: "N data ditemukan" / "Tidak ada data yang cocok" adalah status message); pengalih tampilan = tombol dengan `aria-pressed`; perubahan segmen memindahkan fokus ke heading segmen.
- **Teks medis**: `text-base` minimum, tanpa `truncate`/`line-clamp` (dilarang di data medis); kompatibel WCAG 1.4.12 (line-height ≥1,5×).
- **Fokus terlihat** via `--ring`; label `Label`+`Input` pada pencarian; axe (`web/tests/e2e/a11y.ts`) wajib 0 pelanggaran + pemeriksaan keyboard/manual tetap dijalankan.

## 9. Privasi

- Data medis (diagnosis, keluhan, isi surat, nama dokter-pasien, tanggal konsultasi) **tidak** muncul di: toast (sonner), judul tab, URL, atau notifikasi. URL hanya id numerik (`/rekam-medis/42`); token QR hanya di query verifier publik (aturan `_global.md`).
- NIK selalu masked (`formatNikMasked`); daftar menampilkan nomor resep/tanggal saja — **isi klinis hanya di detail** (prinsip data minim; UU PDP 27/2022 Pasal 5 hak informasi + Pasal 34 keamanan).
- **Transparansi akses**: copy "aksesnya dicatat" di detail = kewajiban memberi tahu (selaras Permenkes 24/2022 jejak akses; bukti pola: SATUSEHAT memberi tahu pasien saat nakes melihat datanya, 2026-10-01). Pengungkapan *log lengkap* ke pasien butuh endpoint + keputusan kebijakan (Pertanyaan terbuka #3) — **jangan** ditampilkan karangan.
- **Unduhan/print**: warning wajib "hapus dari perangkat bersama" (pola NHS App, 2026-10-01); file cetak tidak diberi nama yang memuat diagnosis (nama file dikontrol browser saat print; jangan membocorkan data lewat `document.title` sementara — judul tetap generik "Rekam medis | Sehatly").
- Error/404/403 tidak pernah menampilkan cuplikan data medis; pesan generik.
- Segmen riwayat kunjungan menampilkan `keluhan` (kata pasien sendiri) hanya di layar milik akun; tidak dikirim ke toast/log frontend.

## 12. Pertanyaan terbuka

1. **Endpoint daftar rekam medis — DEPENDENSI UTAMA.** `flows.md` mencatat "tidak ada endpoint daftar rekam medis (index menurunkan id dari resep)". Tambah `GET /rekam-medis` (mis. `?q=&tanggal_dari=&tanggal_sampai=&page=`) untuk pasien (milik sendiri) + dokter? Tanpa ini: (a) rekam medis **tanpa resep tak pernah muncul**, (b) pencarian isi rekam medis mustahil **di sisi klien tanpa membakar N baris log akses**, (c) linimasa tidak resmi. Keputusan pemilik produk: tambah endpoint (disarankan — baca daftar tidak perlu 1 log per baris; cukup 1 event "daftar dibuka") vs pertahankan turunan-resep.
2. **Unduh/ekspor resmi**: pola acuan (Halodoc/MyChart) memakai **unduh PDF**; Sehatly hanya bisa print browser hari ini (`file_url` surat = `NULL`, tidak ada endpoint ekspor). Setujui print-interim sekarang, atau tunggu endpoint `GET /rekam-medis/{id}/unduh` (PDF server-side)? Jika endpoint dibuat: format apa (PDF/JSON/CSV) dan apakah membacanya menulis log tersendiri?
3. **Log akses dibaca pasien?** Backend sudah mencatat setiap baca (`akses_rekam_medis_log`, `tujuan_akses: pasien_sendiri/perawatan/audit`) tapi **tidak ada endpoint pembacaan**. SATUSEHAT memberi tahu pasien saat nakes membuka data (bukti 2026-10-01) dan UU PDP memberi hak tahu pemrosesan. Tambah `GET /rekam-medis/{id}/akses` (atau notifikasi F11)? Perlu keputusan kebijakan: tampilkan siapa (nama dokter? peran saja?).
4. **Relasi booking ↔ rekam medis**: `BookingResource` tidak punya `konsultasi_id`, `KonsultasiResource` tidak punya `rekam_medis_id` → "Riwayat kunjungan" tidak bisa menaut ke rekam medis terkait. Tambah FK di resource, atau terima segmen terpisah?
5. **PDF surat keterangan**: `SuratKeteranganService` sengaja mengeset `file_url = NULL` ("no PDF is rendered"). Pasien perlu unduh surat sakit/rujukan? (Butuh renderer PDF baru — lingkup backend.)
6. **Halaman verifikasi QR**: endpoint publik `GET /surat-keterangan/{nomor_surat}/verify?token=` ada dan selalu 200; apakah F10 membangun rute web `/verifikasi-surat/{nomor}?token=` (token di query = sudah diizinkan `_global.md` §1.2 #4) untuk pihak faskes, atau biarkan pemindaian mengakses API langsung?
7. **Ukuran halaman**: hub memakai `per_page: 50` (cap server 100) untuk daftar turunan, surat/kunjungan `15` + `Pagination` — setujui, atau seragamkan?
8. **Setelah endpoint daftar ada**: apakah turunan `daftarRekamMedis()` dihapus dari hub (tetap dipakai untuk fallback offline), dan bagaimana perannya di `/konsultasi`?
9. **Peran dokter di F10**: daftar turunan menjawab 403 untuk dokter. Perlu `GET /rekam-medis` untuk dokter (catatan "a doctor's own consultation list is a real server-side gap" sudah ada di kode), atau dokter cukup lewat konsultasi masing-masing?
