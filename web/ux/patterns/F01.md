> 4. **Tidak ada biometrik/passkey** di stack web (WebAuthn butuh endpoint challenge baru). Jangka pendek: perangkat tepercaya + sesi refresh 30 hari; passkey = fase berikutnya (§12 #2).

## 1. Tujuan pengguna dan metrik sukses

- Peran: **pasien** (Android kelas menengah-bawah, jaringan tidak stabil, muda–lansia). Data kesehatan sensitif; UU PDP berlaku.
- Tujuan pengguna:
  1. Mendaftar dengan **jumlah field yang wajar** dan tahu **mengapa** nomor telepon diminta.
  2. Menerima dan memasukkan kode 6 digit **tanpa menebak**: tahu sisa waktu, tahu cara minta kode baru, tahu apa yang salah bila kode ditolak.
  3. Tidak terkunci di layar OTP saat kode kedaluwarsa/tidak datang.
  4. Tahu dan bisa mengendalikan **perangkat mana yang masih masuk**.
- Metrik terukur:
  - Login: **≤4 layar / ≤6 ketukan** dari `/login` sampai beranda (dengan OTP).
  - Registrasi: field opsional **ditandai opsional** (0 field opsional tampil wajib); isian tidak hilang saat error (AC-9).
  - **0 kasus** pengguna harus kembali ke `/login` untuk memulihkan kode (resend tersedia di layar OTP) — setelah backend siap.
  - Kode kedaluwarsa → aksi pulih **≤1 ketukan**; sisa percobaan terlihat sejak percobaan ke-3.
  - **0** nomor telepon/kode/token di toast, URL, atau judul tab.
  - 100% target sentuh ≥44 px; `autocomplete="one-time-code"` aktif; axe 0 pelanggaran di `/login`, `/register`, `/otp`.

## 3. Yang sengaja TIDAK ditiru

- **Captcha di login/registrasi (Mobile JKN).** Menambah gesekan besar untuk lansia/Android kelas bawah dan sudah dikeluhkan pengguna (ulasan Play, bukan fakta resmi). Sehatly memakai throttle server (5/300 dtk, 10/menit) — pertahankan itu, jangan tambah captcha.
- **Login NIK + password + captcha (Mobile JKN).** Sehatly memakai nomor/email + OTP; jangan meniru identitas NIK.
- **Satu akun = satu perangkat (Gojek).** Memaksa logout perangkat lain tanpa penjelasan; Sehatly memakai daftar perangkat + cabut per perangkat.
- **Biometrik yang mati diam-diam (BCA, 30 hari).** Jika kelak ada biometrik, nonaktif harus diberitahukan di muka dan bisa diaktifkan ulang ≤2 ketukan.
- **Sidik jari/Face ID native sebagai syarat.** Web tidak punya API itu; jangan menjanjikan di copy.
- **Halaman FAQ berisi "Loading…" (SATUSEHAT).** Pelajaran: dokumentasi bantuan harus terbaca tanpa JavaScript.
- **Tidak menyalin** nama merek, ikon, ilustrasi, atau teks template pihak mana pun; semua copy ditulis ulang Bahasa Indonesia.

**OTP (`/otp`)** — judul `Kode OTP`; deskripsi: `Masukkan 6 digit kode yang dikirim ke {nomor tersamarkan}.`

**Perangkat (`/profil/perangkat`)** — baru:

### 4.4 Data/API

**[SIAP — dapat dibangun sekarang]**
- `POST /auth/register` — 9 field (`RegisterRequest.php:50-85`); respons `data.user` + `data.otp`.
- `POST /auth/login` — `{no_telepon|email, password}`; respons `data.otp`.
- `POST /auth/otp/verify` — `{kode, tujuan, email|no_telepon, device_id}` (`VerifyOtpRequestBody`, `openapi.yaml:6054-6084`); sukses → `data.user` + `data.token` (Bearer + refresh 30 hari).
- `GET /auth/devices`, `POST /auth/devices`, `DELETE /auth/devices/{deviceId}` — `StoreDeviceRequest`: `device_id`, `platform`, `fcm_token?`, `app_versi?`.
- `POST /auth/refresh` — rotasi + deteksi replay; 401 → sesi berakhir.
- `POST /auth/logout` — mencabut refresh + menghapus access + menonaktifkan **semua** `user_devices`.
- Masking identifier sudah ada (`pending-otp.ts:103`); timer dari `kedaluwarsa_at` + `ttl_detik` sudah ada.

**[USULAN — butuh backend baru]**
1. **`POST /auth/otp/resend`** body `{ tujuan, no_telepon? , email?, device_id? }`, rate limit sendiri (mis. 3/5 menit per akun + IP), respons `{ otp: { kedaluwarsa_at, ttl_detik, kanal } }`; wajib menutup kode lama (perilaku `OtpService::issue()` sudah begitu) dan **tidak** membocorkan apakah akun ada (balas generik). Alasan: `login` butuh password; memegang password di memori halaman OTP adalah risiko.
2. **Normalisasi nomor** `08xx` ↔ `+628xx` di register/login/lookup + backfill data; unique index pada bentuk ternormalisasi. **(P0 kebenaran.)**
3. **Sisa percobaan + alasan burn** di respons 422/429 (mis. `meta.sisa_percobaan`) agar UI bisa jujur.
4. **Consent saat daftar** (lihat §12 #1) — opsi A: field `persetujuan: {syarat_ketentuan: true, kebijakan_privasi: true}` di register (ubah kontrak + FormRequest); opsi B: setelah verify sukses, rute wajib ke layar consent F02 sebelum AppShell.
5. **Perangkat:** `GET /auth/devices` saat ini tidak memuat `device_id` (hanya id internal?) — perlu memastikan UI punya penanda "perangkat ini" (bisa dari device_id lokal). Perilaku logout semua perangkat perlu keputusan §12 #3.

## 7. Edge case medis dan bisnis

1. **Nomor sama mendaftar ulang** (belum terverifikasi): register mengembalikan 422 `no_telepon` unik. UI harus menawarkan `Lanjutkan verifikasi` lewat login, bukan dead-end.
2. **Nomor dinormalisasi ganda** (`0812…` vs `+62812…`): setelah backend normalisasi, akun lama mungkin duplikat → jalankan skrip gabung/atau blokir sementara dengan pesan jelas (keputusan pemilik).
3. **Kode dikirim ke WhatsApp tetapi pengguna tidak punya WhatsApp**: kanal harus bisa ditukar (usulan resend), atau jelas sejak awal kanal mana yang dipakai.
4. **Kode kedaluwarsa saat pengguna mengetik digit terakhir**: jangan buang isian; tampilkan banner + tombol kirim ulang, fokus tetap.
5. **Dua perangkat / dua tab meminta kode**: `issue()` menutup kode lama; tab pertama akan gagal dengan "kedaluwarsa" — pesan harus mengarahkan ke kirim ulang, bukan menyalahkan pengguna.
6. **Percobaan ke-6 membakar kode `login`** (bukan kode registrasi): UI wajib menjelaskan sebelum terjadi; setelah dibakar, tombol verifikasi tidak boleh terus aktif tanpa harapan (arahkan ke kirim ulang).
7. **Akun `pending_verifikasi`** mencoba login lagi: `login` menerbitkan kode `login`; setelah verifikasi sukses status menjadi `aktif` — jangan tampilkan dua makna status.
8. **Akun `nonaktif`/`ditangguhkan`** (403): tampilkan pesan server + kanal bantuan; jangan menawarkan OTP.
9. **Ganti nomor telepon** belum ada alurnya; tampilkan sebagai `Segera hadir`? — **jangan**; cukup jangan tampilkan sampai ada backend (keputusan §12 #4).
10. **Lansia/tanpa email**: email opsional harus tetap opsional; login dengan telepon saja harus bekerja (sudah).
11. **Perangkat hilang**: tanpa passkey/biometrik, pemulihan = login OTP di perangkat baru + cabut perangkat lama dari daftar (setelah UI ada).
12. **Replay refresh token**: server sudah mencabut semua sesi → UI menampilkan `Sesi berakhir` dan tidak loop refresh (sudah ditangani `http.ts`).

## 8. Aksesibilitas

- **Urutan fokus login:** toggle Telepon/Email → input identifier → `Lanjutkan` → footer `Daftar`. Registrasi: kelompok Data akun → Data diri → checkbox consent → `Daftar`.
- **OTP:** fokus otomatis ke slot 1 saat halaman dibuka; satu field logis (6 slot) — screen reader mengumumkan `Masukkan 6 digit kode`; setelah error, fokus kembali ke slot 1 dan `aria-describedby` menunjuk pesan error (jangan mengumumkan ulang seluruh halaman).
- **Timer:** `role="timer"` dengan `aria-live="off"` untuk hitung mundur per detik (jangan spam pembaca layar); perubahan status ke "kedaluwarsa" diumumkan `role="status"` `aria-live="polite"`.
- **Target sentuh ≥44 px** untuk slot, tombol, chip toggle; jarak antar-slot ≥8 px.
- **Kontras ≥4,5:1**; timer `--muted-foreground` hanya jika lolos kontras, jika tidak pakai `--foreground`.
- **Teks besar:** dukung zoom 200%; jangan `truncate` pada nomor tersamarkan/error.
- **Keyboard:** slot dapat diisi dengan angka, Backspace mundur, panah kiri/kanan, paste 6 digit mengisi semua slot.

## 9. Privasi

- **Yang tampil:** nomor telepon **disamarkan** (`0812****7890`); email disamarkan bila dipakai; nama lengkap hanya setelah login.
- **Tidak boleh muncul** di toast, URL, judul tab, `aria-label`, atau log konsol: kode OTP, token akses/refresh, nomor penuh, `device_id`.
- **`POST /auth/otp/verify` tidak boleh membocorkan** apakah akun ada — server sudah menyamakan pesan (`tidak_diketahui`); UI tidak boleh menambah pesan yang membedakan.
- **Peringatan berbagi kode** di layar OTP dan template pesan (`Jangan bagikan kode ini…`).
- **UU PDP 27/2022:** tujuan pengumpulan nomor telepon dinyatakan di form; consent dicatat sebagai ledger (F02) dengan versi dokumen; pengguna dapat melihat status persetujuan di `/profil/privasi`.
- **Log/analytics:** jangan kirim nomor/kode ke event analytics; gunakan id internal.
- **Perangkat:** daftar perangkat adalah data pribadi; hanya tampil untuk pemilik akun (sudah dijaga `auth:sanctum`), dan cabut perangkat milik akun lain tetap 404 (sudah diuji).

## 12. Pertanyaan terbuka

1. **Consent saat daftar — mana yang dipilih?** (a) tambah field consent di `POST /auth/register` (perubahan kontrak + FormRequest) atau (b) setelah verify sukses, paksa layar consent F02 sebelum masuk aplikasi? Saat ini server tidak menerima consent saat daftar; tautan S&K sudah ada. **Butuh keputusan pemilik.**
2. **Passkey/biometrik: fase berapa?** Butuh endpoint challenge WebAuthn + perubahan model sesi; tidak ada di stack. Jangka pendek diusulkan **perangkat tepercaya** (refresh 30 hari + daftar perangkat). Setuju?
3. **Logout sekarang mematikan SEMUA perangkat** (`AuthController::logout` :373-376). Apakah perilaku yang diinginkan, atau logout seharusnya hanya perangkat ini? (UI daftar perangkat akan membingungkan bila logout = global.)
4. **Ganti nomor telepon**: belum ada alurnya. Alur baru (OTP ke nomor lama + baru) atau cukup lewat CS di fase ini?
5. **Kanal OTP**: aktifkan WhatsApp (Fonnte sudah ada) sebagai opsi/utama, dan izinkan pengguna memilih? Ini memengaruhi copy + endpoint resend.
6. **Sisa percobaan**: mau mengekspos penghitung di API (disarankan) atau cukup pesan generik 429? Menampilkan sisa percobaan menuntut perubahan respons `OtpRejected`.
