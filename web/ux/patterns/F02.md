## 1. Tujuan pengguna dan metrik sukses

- **Peran utama:** pasien (Android kelas menengah-bawah, termasuk lansia). Turunan:
  dokter (menghadapi 403 saat menerbitkan surat keterangan ber-rujukan bila pasien belum
  menyetujui berbagi data), serta perawat/kurir/admin yang baris persetujuannya sama-sama
  nyata (`auth:sanctum` saja, tanpa guard peran — `routes/api.php:1316-1322`).
- **Tujuan:** memahami **lima jenis persetujuan** dalam bahasa sederhana, mengambil
  **satu keputusan eksplisit per slot**, dan **menariknya kapan saja** tanpa bantuan siapa pun.
- **Metrik terukur:**
  - **≤ 1 ketukan** dari menu "Privasi dan data" sampai satu keputusan tercatat (tanpa field) — M-1.
  - **≤ 3 ketukan** untuk menarik satu persetujuan (baris → dialog → konfirmasi) — M-2.
  - **0 field teks** untuk memberi/menarik persetujuan — M-3.
  - **5 slot selalu tampil** dalam urutan DDL, tidak pernah ada slot hilang — M-4.
  - **0 kotak/pilihan yang sudah tercentang** saat `efektif = null` — M-5.
  - **100%** kontrol ≥ 44 px, kontras ≥ 4,5:1, axe bersih, status teks+ikon+warna — M-6.

## 3. Yang sengaja TIDAK ditiru

- **Halodoc (RED FLAG — tidak boleh jadi sumber pola):** persetujuan pemasaran terbungkus
  dalam "menggunakan Platform" dan persetujuan pihak ketiga dianggap ada
  (`halodoc.md` [halodoc#1], akses 2026-10-01). Di Sehatly: **setiap slot terpisah,
  tanpa implikasi, tanpa bundling** — menolak promosi tidak memengaruhi layanan lain.
- **SATUSEHAT Mobile:** tidak ada satu pun layar yang bisa diamati → **tidak ada elemen yang
  diambil** (`satusehat-mobile.md`). Deklarasi data safety dua toko yang bertentangan tidak
  ditiru sebagai cara memberi informasi.
- **Apple Health:** (a) alur berbagi 6 langkah + pemilihan topik → terlalu banyak keputusan
  untuk lima slot tetap Sehatly; (b) **cadangan iCloud default aktif** (`apple-health-sharing.md`
  [apple#3]) — opt-out default tidak dipakai; (c) kontrol per-kategori memakai `switch`,
  sedangkan `ui/switch` tidak ada di kit — dipakai `ToggleGroup` yang sudah ada.
- **MyChart:** (a) **durasi akses** ("how long the app has access") tidak disalin — API
  Sehatly tidak punya masa berlaku persetujuan (`StorePersetujuanPdpRequest` hanya menerima
  `jenis`, `versi_dokumen`, `disetujui`); (b) alur proxy/undangan keluarga + formulir kertas
  di luar cakupan; (c) semua teks/layar asli tidak disalin — hanya pola interaksi.
- **EDPB "cookie wall"/scrolling** (par. 38–41/86) tidak relevan: F02 bukan banner cookie.
- Nama merek, ikon khas, ilustrasi, dan teks pihak ketiga **tidak disalin**; seluruh copy
  ditulis ulang untuk Sehatly.

    disetujui_at: ISO-8601 UTC|null, ip_address: string|null }`; `meta` = top-level sibling
    `singlePageMeta(5)`. Query key: `['v1','pdp','persetujuan']`.

    **422** (`errors.versi_dokumen` = **2 pesan**). Kolom `id`, `user_id`, `disetujui_at`,

- **Aturan versi (KOREKSI pemilik 2026-10-01 — server adalah otoritas):** `GET /api/v1/pdp/dokumen`
  mengembalikan versi **aktif** + `berlaku_sejak` per `jenis`. `POST` **menolak** versi yang bukan
  versi aktif (422 `errors.versi_dokumen`) → klien refetch `GET /pdp/dokumen`; klien **tidak lagi
  mengarang versi**. `persetujuan_pdp` menjadi **ledger append-only**: status terkini = catatan
  terbaru per `(user, jenis)`; **penarikan boleh kapan saja pada versi yang sama** (bukan hanya saat
  dokumen maju); keputusan sama berurutan = idempoten. Format versi tetap zero-pad `v01`…`v99`.
  *Backend dikerjakan lebih dulu (sesi backend) sebelum UI dirilis.*
  - API adapter: `web/src/lib/api/pdp-persetujuan.ts` berisi `persetujuanOptions()` dan
    `catatPersetujuanMutation()` memakai `request()` dari `@/lib/http` (pola
    `lib/api/pasien-profil.ts`).
  - **Realtime (Reverb): tidak ada** (F02 bukan kanal `konsultasi.{id}`) → refetch setelah
    mutasi, tanpa polling.

## 6. State lengkap

| State | Yang dilihat pengguna | Tindakan lanjut |
|---|---|---|
| Loading | `SkeletonRows rows={5}` dalam `LoadingState` berlabel "Memuat persetujuan…" — bukan spinner layar penuh | — |
| Kosong (tidak mungkin dari API) | GET selalu 5 entri; bila **semua** `efektif = null` → `EmptyState` kompak "Belum ada keputusan Anda…" di atas daftar (daftar tetap dirender) | pilih jawaban per slot |
| Belum dijawab (parsial) | Baris tanpa pilihan terpilih + badge "Belum dijawab"; tidak ada peringatan merah | pilih Setujui/Tidak setujui |
| Error jaringan (GET) | `ErrorState` "Gagal memuat persetujuan." + "Coba lagi" (refetch) | retry |
| Error saat simpan (5xx/network) | `Alert` `role="alert"` pada baris: "Gagal menyimpan keputusan. Coba lagi." — pilihan tidak hilang | retry (kirim ulang) |
| 422 versi (tabrakan / lebih lama) | `Alert` `role="alert"` memuat pesan **pertama** `errors.versi_dokumen` + "Menampilkan data terbaru dari server."; **tidak ada retry otomatis** → GET ulang, state mengikuti `efektif` | membaca ulang; bila masih tabrakan → tombol "Muat ulang" |
| Offline | `OfflineBanner` + semua `ToggleGroupItem`/tombol `disabled` (tanpa antrean mutasi — `_global §7 #1`) | kembali online → banner hilang, tombol aktif |
| Sesi habis | Refresh single-flight → redirect `/login` (perilaku global F15) | login → kembali `/profil/privasi` |
| Sukses (201) | Badge + kolofon berubah + `Alert` `role="status"` "Persetujuan dicatat." | lanjut ke slot berikutnya |
| Idempoten (200) | Pesan yang sama "Persetujuan dicatat." (respons menyatakan sudah tercatat, tidak berubah) | — |
| Gate 403 (layar dokter) | `ForbiddenState` dengan pesan server **+** "Minta pasien menyetujui berbagi data medis di Profil → Privasi dan data." (tanpa tombol coba lagi yang pasti gagal) | kembali ke daftar surat keterangan |

## 7. Edge case medis dan bisnis

1. **Penarikan (withdrawal):** keputusan pada satu versi bersifat **abadi**; penarikan = baris
   baru `disetujui:false` pada versi **lebih tinggi** (aturan §4). Setelah penarikan, gate
   `berbagi_data_medis` ikut menolak (baca selalu versi tertinggi). Baris lama tidak pernah
   dihapus (jejak audit + `audit_log`).
2. **422 tabrakan versi sama** (dua perangkat mengirim jawaban berbeda pada versi sama):
   **jangan retry** (identik byte → identik ditolak); GET lalu ikuti `efektif`; tampilkan
   pesan server + "Menampilkan data terbaru" (instruksi `PersetujuanPdpController`).
3. **422 versi lebih lama** (klien memegang versi basi): penanganan sama dengan #2 dengan
   pesan "Versi dokumen ini lebih lama dari versi yang sudah tercatat."
4. **Persetujuan dibutuhkan sebelum tindakan kesehatan:** penerbitan surat keterangan
   ber-rujukan memanggil `PdpConsent::require(pasien, 'berbagi_data_medis')` **sebelum tulis
   dan dalam transaksi** → 403 "Persetujuan berbagi data medis tidak diberikan oleh pasien.";
   UI dokter = `ForbiddenState` + panduan meminta izin (bukan tombol coba lagi). Konsultasi,
   resep, dan booking **tidak** diblokir gate ini.
5. **Anak / wali:** Permenkes 24/2022 Pasal 34 mengizinkan persetujuan keluarga/wali untuk
   pasien tidak cakap, tetapi `persetujuan_pdp.user_id` menunjuk **akun**, bukan `pasien`
   → persetujuan anak yang tidak punya akun **tidak dapat direpresentasikan**. Solusi sementara: data anggota keluarga dicatat di akun wali (`/profil/keluarga`), dan persetujuan wali atas akunnya sendiri. **Jangan menebak**; lihat Pertanyaan #5.
6. **Offline:** deteksi `navigator.onLine` → banner + tombol nonaktif; **tidak ada antrean
   mutasi** (`_global §7 #1`); tidak ada input yang hilang karena F02 tanpa field.
7. **Dua perangkat / kirim ganda:** POST idempoten (200 bila versi+jawaban sama) → kedua
   perangkat melihat baris yang sama setelah refetch; audit_log tetap satu baris.
8. **Ketidakkonsistenan urutan string versi:** semua versi klien `v01`…`v99`; `naikVersi()`
   **melebar ke 3 digit bila mentok di `v99` → hentikan, jangan kirim**; angkat ke
   Pertanyaan #1 (format `v0001` bila perlu).
9. **Menolak `pemasaran`/`komunikasi_tindak_lanjut`:** tidak pernah memengaruhi akses
   layanan (tidak ada `require()` di endpoint lain untuk dua jenis itu) — kalimat di UI
   menyatakan itu, agar tidak terasa sebagai consent wall.
10. **Admin:** `pdp.kelola` sengaja **tidak** dipakai route mana pun → **tidak ada** UI yang
    mengubah persetujuan orang lain; permukaan admin (bila ada) hanya baca.
11. **Zona waktu:** `disetujui_at` = ISO-8601 UTC dari server → tampilkan dikonversi ke zona
    perangkat **dengan label** (`WIB/WITA/WIT`) sesuai `_global §5`.
12. **Realtime:** tidak ada; jangan menampilkan indikator "diperbarui langsung".

## 8. Aksesibilitas

- **Urutan fokus:** kembali → pengantar → per slot: judul → "Baca selengkapnya" → pilihan →
  aksi (tarik/setujui). Tidak ada fokus tersembunyi di balik modal (dialog mengunci fokus
  Radix dan mengembalikannya ke pemicu).
- **Label:** tiap `ToggleGroupItem` diberi `aria-label` lengkap, mis. "Setujui Kebijakan
  privasi" / "Tidak setujui Kebijakan privasi" — nama + tujuan, bukan hanya "Setujui".
  Semua kontrol interaktif punya teks terlihat (WCAG 3.3.2).
- **Target sentuh ≥ 44 px:** `ToggleGroupItem className="h-11"` (bawaan `h-9`), tombol
  `size="lg" className="h-11"`, pemicu `Collapsible min-h-11`. WCAG 2.5.8 (AA) hanya 24 px;
  ambang Sehatly mengikuti 2.5.5 (44 px).
- **Kontras:** teks `--foreground`/`--muted-foreground` di atas `--card` ≥ 4,5:1 (1.4.3);
  border status & ikon ≥ 3:1 (1.4.11). Warna **tidak pernah sendirian** — selalu teks + ikon.
- **Pengumuman pembaca layar:** baris yang berubah = `role="status"` `aria-live="polite"`,
  e.g. "Kebijakan privasi: Disetujui, versi v01."; kegagalan 422/5xx = `role="alert"`;
  status badge memakai teks yang terbaca ("Disetujui", bukan hanya warna).
- **Fokus terlihat** via token `--ring`; tanpa `outline-none` yang tidak diganti.
- **Teks besar / zoom 200%** (1.4.4): tinggi baris memakai padding, bukan tinggi tetap;
  teks panjang wrap penuh (tanpa `truncate`) pada judul dan tujuan slot.
- **Keterbacaan:** kalimat ≤ 15 kata, tanpa istilah hukum ("eksplisit", "retensi",
  "pemrosesan" dihindari pada copy; ganti dengan "Anda memilih", "berapa lama disimpan",
  "cara data dipakai") — selaras UU PDP Pasal 22 (bahasa sederhana) [uu-pdp#2].

## 9. Privasi

- **Tampil di halaman:** 5 slot, status, tujuan, versi dokumen, waktu keputusan (berlabel),
  dan `ip_address` **hanya di detail terlipat** (baris milik akun itu sendiri).
- **Tidak tampil:** tidak ada data medis di F02 sama sekali (tidak ada nama obat, dosis,
  diagnosis, isi konsultasi) → **toast, judul tab, dan URL** hanya memuat generik: judul tab
  "Privasi dan data", URL `/profil/privasi` tanpa parameter, toast (bila dipakai) tanpa
  isi medis.
- **Tanpa pra-centang:** `efektif=null` → tidak ada pilihan terpilih; keputusan = aksi
  eksplisit (EDPB/ICO [edpb#3]); penolakan setara penerimaan (tombol sama besar/contrast).
- **Penarikan selalu terlihat** di baris yang sudah disetujui (bukan disembunyikan di menu)
  — UU PDP Pasal 9 [uu-pdp#3]; setelah tarik, baris tetap menampilkan "Tidak disetujui" +
  waktu (bukti keputusan).
- **UU PDP:** tujuan per slot tampil sebelum keputusan (Pasal 21) [uu-pdp#4]; masa simpan
  catatan disebut singkat (Pasal 21 huruf d — draft di Pertanyaan #3); akses/koreksi data →
  `/profil` (Pasal 5–7); efektivitas keputusan tertinggi = penghentian pemrosesan berbasis
  persetujuan (Pasal 40 dijalankan backend lewat aturan versi).
- **Yang tidak boleh dikirim/ditampilkan:** `user_id`, `disetujui_at`, `ip_address`, `id`
  **tidak pernah dikirim dari klien** (server `prohibited`); jangan tampilkan IP di toast
  atau notifikasi; jangan taruh `versi_dokumen`/status di URL.

## 12. Pertanyaan terbuka

**Diputuskan pemilik 2026-10-01:**
- **#1 versi & penarikan (gabungan B+C):** server otoritas lewat `GET /pdp/dokumen`; `POST` menolak
  versi non-aktif; `uq_consent` → ledger **append-only**; penarikan **instan pada versi yang sama**;
  keputusan sama berurutan idempoten. Backend lebih dulu, dengan tes Pest: versi non-aktif ditolak;
  tarik→setujui ulang pada versi sama berhasil; consent pasien lain tak bisa dibaca/ditulis. UI F02
  dikembangkan dengan mock Playwright dan **belum dirilis sebelum backend selesai**.
- **#2 teks dokumen:** halaman statis `/kebijakan-privasi` + `/syarat-ketentuan` + tautan "Baca
  kebijakan lengkap" dari tiap slot.
- **#4 pendaftaran:** F01/`AuthRequest` **tidak** diubah. Halaman daftar menampilkan **satu baris
  pemberitahuan + tautan** (tanpa checkbox). F02 menjadi **gerbang wajib sebelum booking atau
  pembayaran pertama** untuk consent wajib (syarat, kebijakan privasi, pemrosesan data kesehatan).
  Menelusuri direktori dokter **tidak** digerbang. Consent opsional (riset, pemasaran, analitik)
  default **mati** dan tidak pernah menjadi gerbang. `/profil/privasi` tetap bisa dibuka kapan saja.

**Masih terbuka:**
- **#3 kalimat masa simpan (Pasal 21 UU PDP)** — masih draft; konfirmasi kebijakan retensi resmi.
- **#5 anak/wali** — butuh keputusan produk + skema backend.

---

*Daftar pertanyaan asli (sebelum keputusan) disimpan di bawah untuk jejak.*

1. **Sumber `versi_dokumen` dan aturan penarikan (KRITIS).** Tidak ada endpoint yang
   menyatakan "versi dokumen saat ini" (`GET` hanya mengembalikan versi yang tercatat).
   Pola ini memakai konstanta klien `web/src/lib/pdp/versi-dokumen.ts` dan mengirim versi
   **lebih tinggi dari yang tercatat** untuk setiap perubahan jawaban — mengikuti pesan
   422 API ("Tarik persetujuan dengan mengirim versi_dokumen yang lebih tinggi"), tetapi
   **bertentangan dengan catatan** `PersetujuanPdpController` ("klien tidak boleh
   mengarang versi; penarikan datang saat dokumen maju"). Pilih: **(A)** setujui konvensi
   klien (tanpa ubah backend; risiko: rilis versi nyata berikutnya bisa bertabrakan dengan
   versi penarikan), **(B)** endpoint baru `GET /pdp/dokumen` (versi aktif per `jenis`),
   atau **(C)** aturan backend yang mengizinkan penarikan versi sama (butuh perubahan
   unique key `uq_consent`).
2. **Di mana teks dokumen dibaca?** Tidak ada rute `/kebijakan-privasi` atau
   `/syarat-ketentuan` (dicek di `router.tsx`, 2026-10-01) dan tidak ada endpoint isi
   dokumen. Cukup `Collapsible` ringkasan (pola saat ini), atau buat halaman statis +
   tautan "Baca kebijakan lengkap"?
3. **Kalimat masa simpan (Pasal 21 UU PDP)** pada detail terlipat masih **draft**: "Kami
   menyimpan catatan keputusan ini selama Anda memiliki akun, sebagai bukti persetujuan
   Anda." — konfirmasi dengan kebijakan retensi resmi.
4. **Apakah `syarat_ketentuan`/`kebijakan_privasi` juga diminta saat pendaftaran (F01)?**
   Endpoint F02 hanya mencatat satu keputusan per panggilan, dan `AuthRequest` tidak
   menerima persetujuan (dicek 2026-10-01). Menggabungkannya berisiko jadi consent wall —
   perlu keputusan terpisah.
5. **Anak/wali** (edge #5): perlu skema baru (baris atas akun wali + tautan `pasien_id`,
   atau akun anak) — keputusan produk + backend; jangan diimplementasi tanpa persetujuan.
6. **Nav "Privasi dan data"** untuk semua peran (dokter/perawat/kurir) di grup "Umum"
   sidebar, atau hanya menu Profil pasien? Route API memang terbuka untuk semua peran.
7. **Menampilkan `ip_address`** di detail terlipat (transparansi UU PDP) atau menyembunyikan
   sepenuhnya (mengurangi kebisingan)? Saat ini pola = tampil di detail.
8. **Pemicu bila ada versi dokumen baru** (mis. banner "Kebijakan privasi diperbarui") —
   bergantung F11 dan keputusan #1; di luar cakupan pola ini.
9. **`pdp.kelola`** tetap tanpa konsumen (sengaja; jangan membuat UI admin yang menulis
   persetujuan orang lain) — konfirmasi lingkup permukaan admin.
